# v0.12 一次性交付目标与验收闸门

状态：执行中。本文是交付清单，不是功能已完成声明。玩法规则以 [v0.12 主合同](PRD-v0.12-core-gameplay.md)及其链接的 S01—S10 系统合同为准；实现证据以可复现测试和实机试玩为准。

## 目标

在现有 Swift 单一权威存档、Godot 二维桌面投影上完成「抽卡／手动培养 → 太守自动保供建城 → 武将真实上岗 → 都督自动逐点征服 → 城市独有能力反哺首都与前线」的完整可玩循环。旧存档原子迁移，不重新开一套演示世界；不以完成某一个竖切替代总体验收。

## 缺一不可的交付闸门

|闸门|可观察结果|自动化/人工验收|
|---|---|---|
|P：PRD 与数据|玩家/太守/都督权限、参数单位、状态迁移、失败恢复、每城独有作用和边界案例只有一份有效合同|系统交叉校验；所有待定数值裁决或标实验参数，冲突旧条款有覆盖表|
|G：招募培养|单常驻池、概率保底、重复卡手动处理、60 位有合规来源的唯一武将；新人第一贡献可追踪|固定种子、幂等重试、重启、满 30/60、重复卡不增人口|
|C：自动城市|30→40→50→60 突破、共享住宅和真实供餐、金矿—冶炼—铸币、幸福/伤病/医舍、空闲有原因|多种子 1/7/30 日账本；高伤病、低粮、满员的恢复测试|
|W：天下战役|12 城各逐点、有实际驻防/补给和战损；11 座外城各自许可须实建才生效；袭扰、失点、修复和终局供给审计|逐城条件/效果单测；30 日多种子长时战役，72 小时现实门槛与离线上限|
|U：桌面体验|同一存档管理窗口和可平铺桌面；状态、人物、道路/建筑、资源与战报反映真实事务|Godot 解析/交互烟测、窗口/桌面同步、性能及发热观察、无提示试玩|
|S：发布安全|升级、保存失败、重复命令、损坏文件和备份均不丢掉已有人物、卡或战果|旧档副本迁移、退出重启、故障注入、`git diff --check` 与完整构建|

任一闸门未通过，状态仍为执行中；不得写“完整实现”或推送替代运行窗口来掩盖失败。测试输出需注明使用的规则版本、存档副本、种子、真实/模拟时间、覆盖范围与未过项。

长时审计的“有币立即单抽”只测资源链及高频招募压力，不代表真实玩家愿意点上万次。另须用`--audit-daily-draws 10`从新档测试“开局两抽，此后每个现实日最多十抽”的低频玩家轨迹；其检查点与无限抽轨迹隔离，首都发展、战役可达性和反馈缺口要单独报告，不得用高频审计替代体验验收。

## 实施顺序

1. 冻结 v0.12 主合同及数值/迁移优先级，明确尚未实现项。
2. 在现有 Swift 世界模型中补齐卡池、人口与治理资源闭环；每段完成后保持旧档可读。
3. 补齐战役的真实前线仓储/运输、十一城许可施工效果、袭扰与终局审计。
4. Godot 只投影已提交状态，补足人物职责、战报和阻塞原因；保留桌面平铺。
5. 运行单元、桥接、长时模拟和人工实机验收；按失败证据调参再重测。
